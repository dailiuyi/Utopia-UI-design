# 手机 MR 决斗界面

把本包的海报视觉语言转成能在手机摄像头画面上清楚阅读、触摸操作的 Unity UI。交付范围由当前请求决定：设计请求输出设计，编码请求才修改工程，审查请求只报告问题。

## 已确认的产品约束

- Unity 6，具体 `6000.x`、UI 框架、渲染管线和包版本从目标项目读取。
- 仅 Android / iOS 手机；中文主界面，英文只承担短编号或少量辅助标题。
- 竖屏用于准备与场景重定位；横屏用于战斗。旋转改变布局，不应重复创建决斗场、角色或对局。
- 相机通过重定位算法对齐现实场景，虚拟决斗场在该场景中进行类似《拳皇》的对战。“类似”指呈现参考，不代表已经确认移动、连招、摇杆或攻击键规则。
- 操作方式尚未确定，必须保留可替换模块。直接操控、指令、观战均为候选，不把任一候选当作已经确定的玩法。
- 视觉基准是随包两张赛事海报：**黑黄、中文衬线大标题、切角细框、警示条、机械线稿**。不以作品名推导青蓝 HUD、绿字终端或紫色霓虹风。
- 游戏名称、角色、对战联网方式、最低机型、性能目标、定位 SDK、结算规则均未确认。可使用明确标注的示例，不把示例写成产品事实。

## 按任务读取

1. 始终读取 [视觉规范](references/visual-language.md) 和 [设计变量](assets/design-tokens.json)。有视觉能力时查看 `assets/reference-posters/` 两张参考；不能看图时使用视觉规范中的文字提炼，不声称看过图片。
2. 制作页面、流程或组件时读取 [界面与状态](references/screens-and-states.md)。一次请求只做相关部分，不默认扩展完整游戏。
3. 编码、技术接入方案设计或技术审查时读取 [Unity 接入与验收](references/unity-integration.md)。没有 Unity 工程时，输出接入方案和待绑定事件，不虚构已完成的 Prefab、场景或编译结果。

## 工作方式

先确认当前要交付的页面/组件，以及哪些工程事实可直接读取。只询问会改变布局或实现的缺项；上述已确认信息不重复询问。操作方式未定时，先完成共享战斗 HUD 和模块接口，不阻塞全部设计，也不替用户定下玩法。

先列出页面的主动作、主信息和异常状态，再应用样式。准备页承接海报的强视觉，战斗页优先观看角色、生命值和操作区。不要将整张海报铺在相机画面后方，也不要让纹理降低实景可见度。

颜色、字级、间距、切角和动效取自设计变量；这些是本项目建议起点，并非从海报精确测量的官方数值。已有工程主题变量时进行映射，避免另建一套相互冲突的常量。

定位 UI 必须消费真实状态。设备追踪正常 ≠ 场景重定位成功 ≠ 决斗场绑定完成；动画播放结束不能触发定位成功。UI 不直接重写定位算法、战斗规则或联网逻辑。

## 完成时应交付

按任务规模提供足够复用的信息：页面层级与布局、所用变量、组件及状态、交互/事件绑定、资源清单。编码任务补充接入位置和实际验证结果；纯设计任务不生成大量无用工程骨架。

说明哪些为用户确认、哪些为可调整建议，以及操作方式等仍未确认的部分。分别报告静态预览、Unity Editor、Android 真机、iPhone 真机的验证状态；未执行的项目明确写“未验证”。

## 交付前核对

- 一眼能识别参考海报的黑黄工业气质，中文正文和实景仍清楚。
- 竖屏准备与横屏战斗是分别编排的布局，重要信息及触摸区在安全区域内。
- 两侧生命值、回合状态、暂停/退出可识别，操作模块未定的边界被保留。
- 权限拒绝、定位失败、定位丢失和旋转过渡有可执行的下一步；没有假进度、假成功。
- 无头显、手柄、凝视交互等额外硬件假设；没有将 HTML 预览或模拟运行当作 Unity 真机验收。
